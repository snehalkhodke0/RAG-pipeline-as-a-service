# Deployment Guide: Render + Neon + Vercel

Exact, click-by-click steps to take this from a local docker-compose stack to a live
deployment. All local commands are PowerShell.

## 1. Create a Neon project and get a pooled connection string

1. Go to https://neon.tech and sign up (free tier is enough).
2. Click **Create a project**. Name it `rag-service`, pick a region close to where
   you'll deploy Render (e.g. Oregon to match `render.yaml`'s default region).
3. Once created, open the project's **Dashboard**.
4. In the SQL editor (or via **Tables** → **SQL Editor**), run:
   ```sql
   CREATE EXTENSION IF NOT EXISTS vector;
   ```
   (The Alembic migration also runs this, but Neon requires the extension to be
   allow-listed/enabled at the project level first on some plans — running it
   manually here avoids any ordering issue.)
5. Go to **Connection Details**. Select **Pooled connection** (important — this uses
   PgBouncer, required because Render's free tier + Alembic's short-lived connections
   would otherwise exhaust Neon's direct connection limit).
6. Copy the connection string. It looks like:
   ```
   postgresql://neondb_owner:npg_xxx@ep-xxx-pooler.us-east-2.aws.neon.tech/neondb?sslmode=require
   ```
7. Convert it to the SQLAlchemy async form (`postgresql+asyncpg://`, and asyncpg wants
   `ssl=require` not `sslmode=require`):
   ```
   postgresql+asyncpg://neondb_owner:npg_xxx@ep-xxx-pooler.us-east-2.aws.neon.tech/neondb?ssl=require
   ```
   Save this — it's your `DATABASE_URL` for both the migration step and Render.
   (The backend already disables asyncpg's prepared-statement cache automatically
   for any `asyncpg` URL — see `app/database.py` — specifically so it's safe to use
   behind Neon's transaction-mode pooler without any extra config.)

## 2. Run Alembic migrations against Neon from local PowerShell

```powershell
cd rag-service\backend
.venv\Scripts\Activate.ps1
$env:DATABASE_URL = "postgresql+asyncpg://neondb_owner:npg_xxx@ep-xxx-pooler.us-east-2.aws.neon.tech/neondb?ssl=require"
python -m alembic upgrade head
```
Expected output ends with:
```
INFO  [alembic.runtime.migration] Running upgrade  -> 0001_initial_schema, initial schema
```
Verify in Neon's SQL editor:
```sql
SELECT tablename FROM pg_tables WHERE schemaname='public' ORDER BY 1;
```
You should see all 10 tables (`users`, `api_keys`, `collections`, `documents`,
`chunks`, `ingestion_jobs`, `conversations`, `messages`, `query_logs`,
`rate_limit_buckets`).

## 3. Push to GitHub and create the Render web service

1. If this isn't a git repo yet:
   ```powershell
   cd rag-service
   git init
   git add .
   git commit -m "Initial commit"
   ```
2. Create a new repo on GitHub and push:
   ```powershell
   git remote add origin https://github.com/<you>/rag-service.git
   git branch -M main
   git push -u origin main
   ```
3. Go to https://dashboard.render.com → **New** → **Blueprint**.
4. Connect your GitHub account if you haven't, then select the `rag-service` repo.
   Render detects `render.yaml` at the repo root automatically.
5. Render shows the `rag-service-backend` service it will create from the blueprint.
   Click **Apply**.
6. Before the first deploy finishes, go to the new service's **Environment** tab and
   set the variables marked `sync: false` in `render.yaml` (Render will prompt for
   these during blueprint creation too):
   - `DATABASE_URL` → the Neon pooled connection string from step 1 (asyncpg form)
   - `GROQ_API_KEY` → your key from https://console.groq.com
   - `CORS_ORIGINS` → your future Vercel URL, e.g. `https://rag-service.vercel.app`
     (comma-separated if you have more than one; you can update this after step 4
     once you know the real Vercel URL, then redeploy)
   - `JWT_SECRET` is auto-generated by the blueprint (`generateValue: true`) — leave it.
7. Click **Manual Deploy** → **Deploy latest commit** if it didn't start automatically.
8. Watch the build logs. The image build step (`docker build`) takes a few minutes —
   it installs dependencies and pre-downloads the fastembed model at build time so the
   deployed container never fetches it at runtime.
9. Once live, note the service URL, e.g. `https://rag-service-backend.onrender.com`.
10. Verify:
    ```powershell
    Invoke-RestMethod https://rag-service-backend.onrender.com/health
    ```
    Expected: `{"status":"ok","db":"ok",...}`. The first request after a cold start
    can take 30-50 seconds (see the free-tier notes below) — that's normal.

## 4. Deploy the frontend to Vercel

1. Go to https://vercel.com → **Add New** → **Project**.
2. Import the same GitHub repo.
3. Set **Root Directory** to `frontend` (important — this is a monorepo).
4. Framework preset: **Vite**. Build command `npm run build`, output directory `dist`
   (Vercel usually detects these automatically once the root directory is set).
5. Under **Environment Variables**, add:
   - `VITE_API_URL` → your Render URL from step 3.9, e.g.
     `https://rag-service-backend.onrender.com`
6. Click **Deploy**.
7. Once live, note the Vercel URL, e.g. `https://rag-service.vercel.app`.
8. Go back to Render → your backend service → **Environment** → update
   `CORS_ORIGINS` to this exact Vercel URL → save (triggers a redeploy).

## 5. Keep the backend warm with cron-job.org

Render's free tier spins down the service after 15 minutes of inactivity; the next
request then pays a cold-start cost (container start + Alembic migration check +
already-cached embedding model load — no download, since that's baked into the image
at build time — typically 30-50 seconds). A periodic health-check ping avoids this
for anyone actively using the app.

1. Go to https://cron-job.org and create a free account.
2. Click **Create cronjob**.
3. **Title**: `rag-service keepalive`.
4. **URL**: `https://rag-service-backend.onrender.com/health`.
5. **Schedule**: every 10 minutes.
6. Save. Check the **Execution history** tab after a few minutes to confirm it's
   getting 200 responses.

## 6. Smoke test the live deployment

From PowerShell (replace the URL with your Render URL):

```powershell
$base = "https://rag-service-backend.onrender.com"

$signup = Invoke-RestMethod -Method Post "$base/auth/signup" -ContentType "application/json" `
  -Body '{"email":"you@example.com","password":"correct-horse-battery-staple"}'
$token = $signup.access_token

$key = Invoke-RestMethod -Method Post "$base/keys" -Headers @{Authorization="Bearer $token"} `
  -ContentType "application/json" -Body '{"name":"smoke-key"}'
$apiKey = $key.full_key

$collection = Invoke-RestMethod -Method Post "$base/collections" -Headers @{Authorization="Bearer $apiKey"} `
  -ContentType "application/json" -Body '{"name":"smoke-collection"}'

$form = @{ file = Get-Item ".\some-document.pdf" }
$upload = Invoke-RestMethod -Method Post "$base/collections/$($collection.id)/documents" `
  -Headers @{Authorization="Bearer $apiKey"} -Form $form

# Poll until READY
do {
  Start-Sleep -Seconds 1
  $job = Invoke-RestMethod "$base/jobs/$($upload.job_id)" -Headers @{Authorization="Bearer $apiKey"}
  Write-Host $job.status $job.stage $job.progress_pct
} while ($job.status -eq "QUEUED" -or $job.status -eq "RUNNING")

# Query it (streams as SSE; a plain Invoke-RestMethod against /query returns JSON instead)
Invoke-RestMethod -Method Post "$base/collections/$($collection.id)/query" `
  -Headers @{Authorization="Bearer $apiKey"} -ContentType "application/json" `
  -Body '{"query":"What is this document about?"}'
```

You should see: a JWT and user object from signup, a `full_key` starting with `rag_`,
a collection object, a 202 with `document_id`/`job_id`, the job progressing to
`SUCCEEDED`/`READY`, and finally an `answer` with a `citations` array and `timings`.

## Render free tier constraints

- **512MB RAM.** The fastembed `BAAI/bge-small-en-v1.5` model plus its ONNX runtime
  uses roughly 150-200MB resident; FastAPI/uvicorn/SQLAlchemy plus Python's own
  baseline adds another ~80-120MB. Total steady-state footprint observed locally is
  comfortably under 350MB, leaving headroom under the 512MB cap. There is no
  torch/sentence-transformers dependency anywhere in the stack specifically to keep
  this footprint small — that's why fastembed with local ONNX inference was chosen
  over a heavier embedding library.
- **Spin-down after 15 minutes idle.** Mitigated by the cron-job.org ping in step 5.
  If you skip that, the first request after idle takes 30-50 seconds — this is Render
  restarting the container, not a bug.
- **No persistent disk.** Not needed here — uploaded file bytes are only ever held in
  memory for the duration of the ingestion background task (see README's "Notable
  design decisions"), never written to disk.
- **Single instance / no horizontal scaling on free tier.** The rate limiter and
  ingestion job state are both stored in Postgres rather than in-process memory
  specifically so this deployment would still be correct if you upgraded to a paid
  plan with multiple instances later.
